───────────────────────────────────────
THE END GOAL
───────────────────────────────────────

We are building a fully automated, AI-powered web system that 
helps a coach and author — someone with approximately fifteen 
years of published writing across blogs, articles, newsletters, 
books, talks, and workshops — participate more thoughtfully and 
effectively in online conversations across multiple social media 
platforms.

The system is not a content scheduling tool. It is not a 
marketing tool. It is a reflective thinking partner. Its 
purpose is to improve the quality of the author's participation 
in public dialogue, not the volume of posts they make.

The system works like this at a high level:

1. It monitors social media platforms continuously and finds 
   conversations related to the author's areas of expertise — 
   coaching, leadership, personal growth, spirituality, and 
   community.

2. For each relevant conversation it finds, it searches the 
   author's entire body of writing to retrieve the most 
   relevant ideas, frameworks, and stories they have already 
   written about.

3. Using those retrieved ideas as grounding, it generates 
   three to four thoughtful response drafts in different 
   styles — each one written in the author's voice and 
   rooted in their actual thinking.

4. It presents those drafts to the author in a clean web 
   dashboard where they can review, edit, approve, or reject 
   each one.

5. When the author approves a response, the system posts it 
   directly to the social media platform automatically.

6. Every decision the author makes — approvals, edits, 
   rejections — is stored so the system gradually learns 
   their preferences and improves over time.

The guiding principle of the entire system is:
Help the author identify conversations where they can make 
a genuinely valuable contribution, and help them contribute 
in a way that is insightful, facilitative, grounded in their 
work, and faithful to their voice.

Every comment requires the author's approval before being 
posted. Nothing is ever published autonomously.

───────────────────────────────────────
HOW THE THREE CORE MODULES CONNECT
───────────────────────────────────────

Modules 1, 6, and 7 form one continuous RAG pipeline. 
They are not three separate features — they are three 
stages of the same flow:

Module 1 builds the knowledge store.
Without Module 1 there is nothing to retrieve.

Module 6 searches the knowledge store.
Without Module 6 the generated responses have no grounding.

Module 7 generates responses using what Module 6 retrieved.
Without Module 7 the retrieved context has no purpose.

The pipeline for every single conversation looks like this:

Conversation submitted via POST /conversations/submit
        ↓
Module 6: Extract semantic search query from conversation
        ↓
Module 6: Embed query and search Supabase pgvector
        ↓
Module 6: Rerank results and assemble context block
        ↓
Module 7: Run conversation analysis with Llama 3 or GPT-4o
        ↓
Module 7: If DO_NOT_COMMENT — stop pipeline, mark skipped
        ↓
Module 7: If COMMENT — generate 4 drafts in parallel
        ↓
Store analysis and drafts in PostgreSQL
        ↓
Expose via GET /conversations/{id} for dashboard to display
        ↓
Author reviews in dashboard and approves, edits, or rejects
        ↓
Module 9: Record decision and log to feedback_log
        ↓
Module 9: If approved — mark ready for posting
        ↓
Module 10: Log feedback for future learning

───────────────────────────────────────
VOICE AND PARTICIPATION PRINCIPLES
───────────────────────────────────────

Every response draft the system generates must reflect 
these principles. Bake them into your generation prompts:

Speak as a thoughtful participant not an authority.
Help people think more deeply rather than simply agree.
Find common ground between differing perspectives.
Challenge ideas without diminishing people.
Ask questions that open genuine inquiry.
Make disagreement feel safer and more productive.
Only suggest links when they genuinely help the reader — 
never for self-promotion.

The goal is for readers of the generated responses to 
feel understood, curious, respected, invited into deeper 
reflection, and more capable of engaging with complexity.

The system should sometimes recommend not commenting at 
all. This is a feature not a bug. Quality over quantity 
is the core principle of the entire product.

DATABASE SCHEMA
═══════════════════════════════════════

Generate a complete supabase/schema.sql file that runs 
cleanly in Supabase SQL editor. It must:

Enable the pgvector extension first with:
CREATE EXTENSION IF NOT EXISTS vector;

Then create these tables in this exact order:

TABLE: documents
- id: UUID primary key default gen_random_uuid()
- filename: TEXT not null
- file_type: TEXT not null
- source_type: TEXT 
  (blog / article / book / newsletter / talk / workshop / other)
- title: TEXT
- author: TEXT
- published_date: DATE
- word_count: INTEGER
- status: TEXT default 'processing'
  (processing / ready / error)
- error_message: TEXT
- created_at: TIMESTAMPTZ default now()

TABLE: document_chunks
- id: UUID primary key default gen_random_uuid()
- document_id: UUID references documents(id) on delete cascade
- chunk_index: INTEGER not null
- content: TEXT not null
- token_count: INTEGER
- embedding: vector(1536)
- created_at: TIMESTAMPTZ default now()

Create an ivfflat index on document_chunks(embedding) using 
vector_cosine_ops with lists = 100

Create this RPC function in the schema file:

CREATE OR REPLACE FUNCTION match_documents(
  query_embedding vector(1536),
  match_threshold float,
  match_count int
)
RETURNS TABLE (
  id UUID,
  document_id UUID,
  content TEXT,
  similarity float
)
LANGUAGE SQL STABLE AS $$
  SELECT
    dc.id,
    dc.document_id,
    dc.content,
    1 - (dc.embedding <=> query_embedding) AS similarity
  FROM document_chunks dc
  WHERE 1 - (dc.embedding <=> query_embedding) > match_threshold
  ORDER BY similarity DESC
  LIMIT match_count;
$$;

TABLE: conversations
- id: UUID primary key default gen_random_uuid()
- platform: TEXT not null
  (reddit / bluesky / mastodon / discord / telegram / 
  threads / youtube / facebook / linkedin / instagram / twitter)
- post_url: TEXT
- post_author: TEXT
- original_post: TEXT not null
- full_thread: TEXT
- submitted_at: TIMESTAMPTZ default now()
- analysis_status: TEXT default 'pending'
  (pending / analysed / skipped / error)

TABLE: conversation_analysis
- id: UUID primary key default gen_random_uuid()
- conversation_id: UUID references conversations(id) 
  on delete cascade
- central_topic: TEXT
- key_tensions: JSONB
- viewpoints_represented: JSONB
- emotional_sensitivities: TEXT
- can_add_value: BOOLEAN
- value_reasoning: TEXT
- participation_recommendation: TEXT (COMMENT / DO_NOT_COMMENT)
- recommendation_reason: TEXT
- relevance_score: FLOAT
- created_at: TIMESTAMPTZ default now()

TABLE: response_drafts
- id: UUID primary key default gen_random_uuid()
- conversation_id: UUID references conversations(id) 
  on delete cascade
- style: TEXT not null
  (insightful_contribution / facilitative_question / 
  synthesis_of_viewpoints / constructive_challenge)
- content: TEXT not null
- value_explanation: TEXT
- source_chunk_ids: UUID[]
- source_document_titles: TEXT[]
- include_link: BOOLEAN default false
- suggested_link: TEXT
- status: TEXT default 'pending'
  (pending / approved / edited / rejected / saved / posted)
- edited_content: TEXT
- rejection_reason: TEXT
- approved_at: TIMESTAMPTZ
- posted_at: TIMESTAMPTZ
- created_at: TIMESTAMPTZ default now()

TABLE: feedback_log
- id: UUID primary key default gen_random_uuid()
- draft_id: UUID references response_drafts(id)
- conversation_id: UUID references conversations(id)
- action: TEXT (approved / edited / rejected / saved / posted)
- original_content: TEXT
- final_content: TEXT
- rejection_reason: TEXT
- edit_diff: TEXT
- created_at: TIMESTAMPTZ default now()

TABLE: processing_logs
- id: UUID primary key default gen_random_uuid()
- task_type: TEXT (ingestion / analysis / generation / retrieval)
- reference_id: UUID (document_id or conversation_id)
- status: TEXT (started / completed / failed)
- message: TEXT
- created_at: TIMESTAMPTZ default now()

ROUTER ENDPOINTS:

POST /knowledge/upload
- Accept multipart file upload plus optional metadata fields:

- Return all documents ordered by created_at descending

- Include at top level: total_documents, total_chunks,

- Return full document details
- Include all chunks with chunk_index and content
- Do not return raw embedding vectors

DELETE /knowledge/documents/{document_id}
- Delete document record (chunks cascade automatically)
- Delete file from Supabase Storage
- Return confirmation

POST /knowledge/documents/{document_id}/reindex
- Delete all existing chunks for this document
- Re-download file from Supabase Storage
- Rerun chunking and embedding pipeline as background task
- Return immediately with status reindexing

INGESTION PIPELINE in app/services/ingestion.py:

The pipeline runs as a background task and must handle 
errors gracefully at every step, logging to processing_logs 
and updating the document status to error with the error 
message if anything fails.

Step 1 — Parse:
Download file from Supabase Storage.
Parse to clean plain text using the correct parser for 
the file type.
Clean the text: strip extra whitespace, fix encoding 
issues, remove repeated headers and footers.
Count words and update the documents record.

Step 2 — Chunk:
Use LangChain RecursiveCharacterTextSplitter.
Read CHUNK_SIZE and CHUNK_OVERLAP from environment variables.
Separators in order: double newline, single newline, 
period space, single space, empty string.
Each chunk must record its index and approximate token count.

Step 3 — Embed:
Use LangChain OpenAIEmbeddings with model 
text-embedding-3-small.
Process chunks in batches of 50.
Generate one embedding vector per chunk.
If embedding fails for a batch retry up to 3 times 
with exponential backoff before marking the document 
as error.

Step 4 — Store:
Insert all chunks with their embeddings into 
document_chunks table in a single batch operation 
where possible.
Update document status to ready.
Log task completed in processing_logs.

═══════════════════════════════════════

Build app/services/retrieval.py as a standalone reusable 
service class called RetrievalService.

This service is not exposed as a public API endpoint.
It is called internally by the analysis and generation

other service.

The class must have one primary public method:
retrieve(conversation_text: str) -> RetrievalResult

Where RetrievalResult contains:
- context_block: str (formatted context ready for prompts)
- source_chunks: list of chunk metadata objects each 
  containing chunk_id, document_id, document_title, 
  source_type, content, similarity_score, rerank_score

STEP 1 — QUERY EXTRACTION:
Use the active LLM (Ollama or OpenAI based on LLM_PROVIDER).
Use the prompt template in app/prompts/retrieval.py.
The prompt must instruct the model to identify the core 
topic, question, or tension in the conversation that a 
thoughtful response would need to address, and return 
only a focused semantic search query of 10 to 20 words 
with no social media language or usernames.
Parse the model output to extract just the query string.

STEP 2 — VECTOR SEARCH:
Embed the extracted query using OpenAIEmbeddings.
Call the match_documents Supabase RPC function.
Use SIMILARITY_THRESHOLD and RETRIEVAL_TOP_K from 
environment variables.
Fetch document title and source_type for each result 
by joining with the documents table.
If fewer than 3 results are returned lower the threshold 
by 0.05 and retry once.

STEP 3 — RERANKING:
Pass all results to the active LLM with the conversation 
text and ask it to score each chunk from 0 to 10 for 
how directly and meaningfully it would help contribute 
to this specific conversation.
The prompt must return scores as JSON with chunk_id 
and score fields.
Sort by rerank score descending.
Keep only the top RETRIEVAL_RERANK_TOP_K results.

STEP 4 — CONTEXT ASSEMBLY:
Format the final chunks into a structured context block.
Each chunk must be labelled with its source number, 
document title, and source type.
Separate chunks with a clear delimiter.
Return the context block string plus the full source 
metadata list.

ERROR HANDLING AND RELIABILITY
═══════════════════════════════════════

Every LLM call must be wrapped in retry logic:
- Maximum 3 retries
- Exponential backoff: 2 seconds, 4 seconds, 8 seconds
- On final failure log to processing_logs with status 
  failed and the error message
- Update the parent document or conversation status 
  to error

Every Supabase database call must be wrapped in 
try/except blocks.
Never expose raw database errors to API consumers.
Return clean error responses with HTTP status codes:
  400 for validation errors
  404 for not found
  422 for unprocessable content
  500 for internal errors

All endpoints must return this response envelope:
{
  "success": boolean,
  "data": object or null,
  "error": string or null,
  "timestamp": ISO timestamp string
}
