═══════════════════════════════════════
WHAT YOU ARE BUILDING — READ THIS FIRST
═══════════════════════════════════════

This prompt covers Module 4 of the AI Dialogue 
Enhancer system. You are building the Post Discovery 
and Scoring engine — the automated background 
workers that continuously monitor connected social 
media platforms, fetch relevant posts, score them 
for relevance using AI, filter the best ones, and 
automatically trigger the RAG pipeline to analyse 
them and generate response drafts.

───────────────────────────────────────
SYSTEM CONTEXT
───────────────────────────────────────

The AI Dialogue Enhancer helps a coach and author 
participate more thoughtfully in online conversations. 
The following modules are already built and running:

Module 1  — Knowledge Base Ingestion
Module 2  — Platform API Connections
Module 6  — Knowledge Retrieval (RAG)
Module 7  — Conversation Analysis and Generation
Module 8  — Dashboard Frontend (Next.js)
Module 9  — Approval and Posting Workflow
Module 10 — Feedback and Learning System

Module 4 is the engine that feeds the entire system. 
Without it the author has to manually paste 
conversations into the dashboard. With it the system 
discovers conversations automatically and the author 
simply wakes up to a shortlist of ready-to-review 
drafts every morning.

───────────────────────────────────────
HOW MODULE 4 FITS INTO THE FULL PIPELINE
───────────────────────────────────────

The complete automated pipeline once Module 4 
is running looks like this:

APScheduler triggers discovery worker every 30 min
        ↓
Module 4: Call PlatformFetchService.fetch_from_all_platforms()
  (this is the unified interface built in Module 2)
        ↓
Module 4: Deduplicate posts against already seen posts
        ↓
Module 4: Score every new post using AI relevance scoring
        ↓
Module 4: Filter — keep only posts above score threshold
        ↓
Module 4: Rank filtered posts and keep daily top N
        ↓
Module 4: For each top post call POST /conversations/submit
  (this triggers the Module 7 RAG pipeline automatically)
        ↓
Module 7: Analyses conversation, retrieves from knowledge 
  base, generates 3-4 response drafts
        ↓
Module 8: Author opens dashboard and sees ready drafts
        ↓
Module 9: Author approves, edits, or rejects
        ↓
Module 10: Feedback logged for future improvement

───────────────────────────────────────
WHAT MODULE 4 DOES NOT DO
───────────────────────────────────────

Module 4 does NOT find or join communities. 
That is Module 3 which is not yet built.
For now Module 4 reads the list of communities 
to monitor from a communities configuration 
table in the database. This table is populated 
manually by the author for now and will be 
managed automatically when Module 3 is built.

Module 4 does NOT post responses. That is Module 9.

Module 4 does NOT generate drafts. That is Module 7.
Module 4 simply submits conversations to the 
existing POST /conversations/submit endpoint 
and Module 7 handles everything from there.

═══════════════════════════════════════
SCHEDULER SETUP
═══════════════════════════════════════

Build app/services/discovery/scheduler.py

Use APScheduler's AsyncIOScheduler.

Initialise the scheduler when the FastAPI app 
starts using a lifespan context manager in 
app/main.py. Shut it down cleanly when the 
app stops.

The scheduler runs one job: the discovery worker.

The interval is read from the discovery_settings 
table on startup. If the table cannot be read 
fall back to the DISCOVERY_SCHEDULE_MINUTES 
environment variable.

The scheduler must check discovery_settings.is_enabled 
before every run. If is_enabled is false log that 
discovery is paused and skip the run without 
unscheduling the job. This allows the author to 
pause discovery from the dashboard without 
restarting the server.

The scheduler must also enforce the 
max_conversations_per_day limit by checking how 
many conversations have been submitted today 
(created_at >= today midnight UTC) before 
submitting more. If the daily limit is already 
reached skip submission for that run but still 
fetch and score for the audit log.

Build these functions in scheduler.py:

start_scheduler() -> None
Initialises and starts the AsyncIOScheduler.
Adds the discovery job with the configured interval.
Logs scheduler started to processing_logs.

stop_scheduler() -> None
Shuts down the scheduler gracefully.

reschedule(interval_minutes: int) -> None
Updates the job interval without restarting 
the scheduler. Called when settings change.

get_status() -> SchedulerStatus
Returns whether the scheduler is running, 
the next run time, and the current interval.

trigger_now() -> str
Triggers an immediate run outside the schedule.
Returns a run_id for tracking.

═══════════════════════════════════════
DISCOVERY WORKER
═══════════════════════════════════════

Build app/services/discovery/worker.py

This is the main orchestrator that runs on 
every scheduled or manual trigger.

Build a DiscoveryWorker class with one primary 
public method:

async run(trigger_type: str = 'scheduled') 
-> DiscoveryRunResult

The run method must execute these steps in order:

STEP 1 — INITIALISE RUN:
Create a new record in discovery_runs with 
status running and trigger_type.
Read current settings from discovery_settings.
Check is_enabled — if false mark run as completed 
with message discovery paused and return early.
Check daily conversation count — if 
max_conversations_per_day already reached mark 
run as completed with message daily limit reached 
and return early.
Log run started to processing_logs.

STEP 2 — FETCH COMMUNITIES:
Read all active communities from 
monitored_communities where is_active is true.
Group them by platform:
{
  "reddit": [
    {"community_id": "leadership", 
     "keywords": ["coaching", "growth"]},
    ...
  ],
  "bluesky": [...],
  ...
}
If no communities are configured log a warning 
and return early with a helpful message.

STEP 3 — FETCH POSTS:
Call PlatformFetchService.fetch_from_all_platforms() 
with:
  keywords: all unique keywords across all communities
  communities: the grouped communities dict
  since: the latest last_fetched_at across all 
    communities for each platform, or 24 hours 
    ago if never fetched before
  limit_per_platform: max_posts_per_run from settings

Update last_fetched_at and fetch_count for each 
community that was successfully fetched.
Update posts_fetched count in the discovery_runs 
record.

STEP 4 — DEDUPLICATE:
Call Deduplicator.filter_new(posts) to remove 
any posts that already exist in discovered_posts 
based on (platform, post_id).
Update posts_duplicated count in discovery_runs.
Insert all new posts into discovered_posts with 
status fetched.

STEP 5 — SCORE:
Call Scorer.score_batch(new_posts, settings) 
to score all new posts for relevance.
Update each discovered_post record with its 
relevance_score, relevance_reasoning, and 
status scored.
Update posts_scored count in discovery_runs.

STEP 6 — FILTER AND RANK:
Filter posts where relevance_score >= 
min_relevance_score from settings.
Sort filtered posts by relevance_score descending.
Calculate how many more conversations can be 
submitted today without exceeding 
max_conversations_per_day.
Take only that many top posts.
Mark all other filtered-out posts in 
discovered_posts with status filtered_out.

STEP 7 — SUBMIT TO MODULE 7:
For each top post call Submitter.submit(post).
The submitter calls POST /conversations/submit 
on the existing backend API with the post data.
On success update the discovered_post record 
with status submitted and the returned 
conversation_id.
On failure update with status error and log.
Update posts_submitted count in discovery_runs.

STEP 8 — COMPLETE RUN:
Update discovery_runs record with status completed,
completed_at, duration_seconds, and all counts.
Log run completed to processing_logs with a 
summary message.
Return DiscoveryRunResult with all counts and 
the run_id.

STEP 9 — ERROR HANDLING:
If any unhandled exception occurs during the run:
Update discovery_runs with status failed and 
the error message.
Log to processing_logs with status failed.
Never let the worker crash the FastAPI server — 
all exceptions must be caught at the top level 
of the run method.

═══════════════════════════════════════
RELEVANCE SCORER
═══════════════════════════════════════

Build app/services/discovery/scorer.py

The scorer uses the active LLM (Ollama or OpenAI 
based on LLM_PROVIDER) to evaluate how relevant 
each post is for the author to respond to.

Build a Scorer class with these methods:

async score_batch(
  posts: list[UniversalPost],
  settings: DiscoverySettings
) -> list[ScoredPost]

Scores posts in batches of scoring_batch_size 
from settings. For each batch call score_single_batch.

async score_single_batch(
  posts: list[UniversalPost]
) -> list[ScoredPost]

Sends one LLM call that scores all posts in 
the batch at once to minimise API calls.

The scoring prompt must:

Describe the author as a coach and author with 
fifteen years of experience in coaching, leadership, 
personal growth, spirituality, and community building.

Instruct the model that the author wants to 
participate in conversations where they can make 
a genuinely valuable contribution — not just 
any conversation on these topics.

For each post provide: platform, community, 
author, title if available, first 300 characters 
of content.

Ask the model to score each post from 0.0 to 1.0 
on these four criteria and return the weighted 
average as the final score:

  Topic Relevance (weight 0.35):
  How closely does this post relate to coaching, 
  leadership, personal growth, spirituality, 
  or community? Score 0 if completely off-topic, 
  1 if directly on topic.

  Contribution Opportunity (weight 0.35):
  How much genuine value could the author add 
  to this conversation? Score 0 if the conversation 
  is already saturated or needs no input, 1 if 
  there is a clear gap the author could fill.

  Discussion Quality (weight 0.20):
  How thoughtful and substantive is this conversation? 
  Score 0 if it is superficial, promotional, or 
  toxic, 1 if it is a genuine deep discussion.

  Audience Fit (weight 0.10):
  How well does this audience match the author's 
  typical readership? Score 0 if clearly wrong 
  audience, 1 if perfect fit.

The model must return ONLY valid JSON in this format:
{
  "scores": [
    {
      "post_id": "platform:post_id",
      "final_score": 0.82,
      "topic_relevance": 0.90,
      "contribution_opportunity": 0.85,
      "discussion_quality": 0.75,
      "audience_fit": 0.70,
      "reasoning": "one sentence explanation"
    }
  ]
}

Parse the JSON strictly. If parsing fails retry 
once with explicit JSON-only instruction. If 
second attempt fails assign a score of 0.0 to 
all posts in that batch and log the error.

Also build a score_single method for scoring 
one post individually used when a post is 
submitted manually via the API:

async score_single(post: UniversalPost) -> ScoredPost

═══════════════════════════════════════
ERROR HANDLING AND RELIABILITY
═══════════════════════════════════════

The discovery worker must be completely 
fault-tolerant. A failure in any single 
platform or post must never stop the 
rest of the run.

Platform-level isolation:
Wrap each platform's fetch in its own 
try/except. If Reddit fails still process 
Bluesky, Mastodon, and all others.
Log platform failures to platform_connection_logs.

Post-level isolation:
Wrap each post's scoring and submission 
in its own try/except. A bad post must 
not stop the rest of the batch.

Scheduler resilience:
If the scheduler job raises an unhandled 
exception APScheduler will catch it and 
continue scheduling future runs. But also 
wrap the entire worker run method in a 
top-level try/except to ensure the 
discovery_runs record is always updated 
with failed status even if something 
unexpected happens.

Daily limit enforcement:
The daily conversation limit check must 
happen in two places: at the start of 
the run AND just before each submission 
in case another run submitted conversations 
while this run was in progress. Use a 
database-level check not an in-memory 
counter to ensure accuracy across 
concurrent runs.

Duplicate prevention:
The unique constraint on (platform, post_id) 
in discovered_posts acts as the final 
safety net against duplicates even if 
the Deduplicator misses something. 
Handle the constraint violation error 
gracefully — treat it as a duplicate 
and continue.
