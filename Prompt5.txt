WHAT YOU ARE BUILDING — READ THIS FIRST
═══════════════════════════════════════

This prompt covers Module 3 of the AI Dialogue 
Enhancer system. You are building the Community 
Discovery and Management module — the part of the 
system that automatically finds relevant communities, 
groups, hashtags, and accounts across all connected 
social media platforms, ranks them by relevance, 
presents them to the author for approval, and then 
adds approved ones to the monitored_communities 
table so Module 4 can start monitoring them.

───────────────────────────────────────
SYSTEM CONTEXT
───────────────────────────────────────

The following modules are already built and running:

Module 1  — Knowledge Base Ingestion
Module 2  — Platform API Connections
Module 4  — Post Discovery and Scoring
Module 6  — Knowledge Retrieval (RAG)
Module 7  — Conversation Analysis and Generation
Module 8  — Dashboard Frontend (Next.js)
Module 9  — Approval and Posting Workflow
Module 10 — Feedback and Learning System

Module 3 feeds directly into Module 4. When a 
community is approved and added to 
monitored_communities, Module 4's discovery 
workers will automatically start monitoring it 
on their next scheduled run. No additional 
configuration is needed.

The monitored_communities table already exists 
in the database from Module 4's migration. 
Module 3 reads from and writes to this table. 
It does not recreate it.

───────────────────────────────────────
WHAT MODULE 3 DOES
───────────────────────────────────────

Module 3 has three responsibilities:

RESPONSIBILITY 1 — COMMUNITY DISCOVERY:
Given a set of topics and keywords defined by 
the author, the system searches all connected 
platforms for relevant communities, groups, 
channels, hashtags, and accounts. It also 
accepts a list of specific people to monitor 
and discovers which communities those people 
are active in.

RESPONSIBILITY 2 — COMMUNITY RANKING:
Each discovered community is scored by the AI 
for relevance to the author's areas of expertise 
— coaching, leadership, personal growth, 
spirituality, and community. Communities are 
ranked and presented to the author as a 
shortlist for review.

RESPONSIBILITY 3 — APPROVAL AND ACTIVATION:
The author reviews the shortlist in the dashboard 
and approves or rejects each suggested community. 
Approved communities are added to 
monitored_communities and become active 
immediately. Rejected ones are stored with a 
reason so the system does not suggest them again.

───────────────────────────────────────
TWO DISCOVERY MODES
───────────────────────────────────────

MODE 1 — KEYWORD DISCOVERY:
The author provides a list of topics and keywords. 
The system searches each connected platform for 
communities, groups, channels, and hashtags that 
match those keywords. It evaluates each result 
for activity level, audience fit, and relevance 
to the author's work.

MODE 2 — PEOPLE-BASED DISCOVERY:
The author provides a list of specific people 
they want to monitor — coaches, authors, thought 
leaders in their space. The system finds those 
people's accounts on each platform, identifies 
the communities and conversations they are most 
active in, and suggests those communities for 
monitoring.

Both modes can run together in a single discovery 
run. Results from both are combined, deduplicated, 
scored, and presented together.

PLATFORM SEARCH METHODS
═══════════════════════════════════════

Add new search methods to the existing platform 
connector classes in app/services/connections/.
Do not create new connector files. Add methods 
to the existing ones.

These are the methods to add to each connector:

───────────────────────────────────────
search_communities(
  keywords: list[str],
  limit: int = 20
) -> list[DiscoveredCommunity]
───────────────────────────────────────

Searches the platform for communities, groups, 
channels, or hashtags matching the keywords.
Returns a list of DiscoveredCommunity objects.

Define DiscoveredCommunity dataclass in 
app/services/community/__init__.py:

DiscoveredCommunity:
  platform: str
  community_id: str
  community_name: str
  community_url: str or None
  description: str or None
  member_count: int or None
  activity_level: str  (high/medium/low/unknown)
  discovery_method: str
  discovered_via_keywords: list[str]
  discovered_via_people: list[str]
  raw_data: dict

Activity level is determined per platform:
Reddit: based on subscriber count and posts_per_day
  high if posts_per_day > 10
  medium if posts_per_day > 2
  low otherwise
Bluesky/Mastodon: based on hashtag post frequency
  high if > 50 posts in last 7 days
  medium if > 10
  low otherwise
Discord/Telegram: unknown by default since 
  member counts require being inside the server
YouTube: based on subscriber count
  high if > 100k subscribers
  medium if > 10k
  low otherwise
Threads: based on post frequency on the topic

Platform-specific implementation:

REDDIT:
Use PRAW's subreddit search: 
subreddits.search(keyword, limit=limit)
For each result capture: display_name, 
public_description, subscribers, 
accounts_active, url
Use accounts_active to determine activity level.

BLUESKY:
Use atproto's search to find posts with each 
keyword as a hashtag. Count posts in the last 
7 days. Return the hashtag itself as a community 
since Bluesky communities are hashtag-based.
Also search for starter packs related to keywords 
if the API supports it.

MASTODON:
Use Mastodon.py's trending_tags() to find 
trending hashtags. Filter by keyword relevance.
Also use search with the keyword to find 
relevant hashtags and accounts.

DISCORD:
Discord does not have a public server search API. 
Use the Discord Discovery API endpoint 
(https://discord.com/api/v9/discovery/search) 
with keyword parameters. This is a public 
endpoint that does not require authentication 
but may have rate limits.
If the endpoint is unavailable return an 
empty list and log a warning — do not fail.

TELEGRAM:
Use the Telegram Bot API to search for public 
channels using the inline query endpoint or 
the resolveUsername method for known channels.
Search is limited on Telegram — return what 
is available and log limitations.

THREADS:
Use the Threads Graph API to search for 
posts and topics related to the keywords.
Return topic hashtags as communities.

YOUTUBE:
Use the YouTube Data API search.list endpoint 
with type=channel and the keyword as query.
Return channels as communities.
Also search for playlists related to the 
keyword since playlist communities indicate 
engaged audiences.

───────────────────────────────────────
get_person_communities(
  handle: str,
  limit: int = 10
) -> list[DiscoveredCommunity]
───────────────────────────────────────

Given a person's handle on this platform, 
finds the communities they are most active in.

Platform-specific implementation:

REDDIT:
Fetch the user's recent comment history using 
PRAW's redditor(handle).comments.new(limit=100).
Extract the subreddits they comment in most 
frequently. Return the top ones by comment count.

BLUESKY:
Fetch the person's recent posts using atproto's 
getAuthorFeed. Extract hashtags they use most 
frequently. Return those hashtags as communities.

MASTODON:
Fetch the person's recent toots using 
Mastodon.py's account_statuses(). Extract 
hashtags they use most. Return those hashtags.

DISCORD:
Not feasible to track individual user activity 
across servers without being in those servers. 
Return empty list and log a note.

TELEGRAM:
If the person runs a public channel use 
resolveUsername to find it and return it 
as a community. Otherwise return empty list.

THREADS:
Fetch the person's recent posts using the 
Threads API. Extract hashtags they use. 
Return as communities.

YOUTUBE:
Fetch the person's channel using the handle.
Return their channel as a community to monitor.
Also return channels they have featured or 
collaborated with based on their 
channelSections if available.

COMMUNITY SCORER
═══════════════════════════════════════

Build app/services/community/community_scorer.py

Uses the active LLM to score each discovered 
community for relevance to the author's work.

Build a CommunityScorer class with:

async score_batch(
  communities: list[DiscoveredCommunity],
  topics: list[str]
) -> list[ScoredCommunity]

Scores communities in batches of 15 in one 
LLM call to minimise API usage.

The scoring prompt must:

Describe the author as a coach and author with 
15 years of experience in coaching, leadership, 
personal growth, spirituality, and community 
building who wants to find online communities 
where they can make genuinely valuable 
contributions to discussions.

For each community provide: platform, name, 
description if available, member count if 
available, activity level.

Ask the model to score each community from 
0.0 to 1.0 on these criteria:

  Topic Relevance (weight 0.40):
  How closely does this community discuss 
  coaching, leadership, personal growth, 
  spirituality, or community building?

  Audience Fit (weight 0.30):
  How well does this community's audience 
  match the author's typical readers and 
  the people they want to reach?

  Discussion Quality (weight 0.20):
  Based on the description and activity level, 
  does this community appear to have 
  substantive, thoughtful discussions?

  Contribution Opportunity (weight 0.10):
  Is this a community where an expert voice 
  would be welcomed and valued?

Return ONLY valid JSON:
{
  "scores": [
    {
      "community_id": "platform:community_id",
      "final_score": 0.78,
      "topic_relevance": 0.85,
      "audience_fit": 0.80,
      "discussion_quality": 0.70,
      "contribution_opportunity": 0.65,
      "reasoning": "one sentence explanation",
      "suggested_keywords": ["keyword1", "keyword2"]
    }
  ]
}

The suggested_keywords field is important — 
ask the model to suggest 2 to 5 specific 
keywords to use when monitoring this community 
based on its topic focus.

Parse strictly. Retry once on failure. 
Assign 0.0 on second failure and log error.

═══════════════════════════════════════
DISCOVERY WORKER
═══════════════════════════════════════

Build app/services/community/discovery_worker.py

Build a CommunityDiscoveryWorker class with:

async run(
  trigger_type: str = 'scheduled',
  modes: list[str] = ['keyword', 'people_based'],
  platforms: list[str] = None
) -> CommunityDiscoveryResult

If platforms is None discover on all connected 
platforms. Check platform_connections table to 
get the list of connected platforms.

STEP 1 — INITIALISE RUN:
Create record in community_discovery_runs.
Load active topics from discovery_topics.
Load active people from monitored_people.
Check that at least one topic or person exists.
If neither exists log a warning and return early 
with a helpful message.

STEP 2 — KEYWORD DISCOVERY (if mode includes keyword):
For each connected platform:
  For each active topic:
    Call connector.search_communities(
      keywords=topic.keywords,
      limit=MAX_COMMUNITIES_PER_PLATFORM
    )
  Combine results across all topics for this platform.
  Deduplicate by community_id within the platform.
  Tag each result with which keywords found it.

STEP 3 — PEOPLE-BASED DISCOVERY 
(if mode includes people_based):
For each active person in monitored_people:
  For each platform where they have a handle:
    If that platform is connected:
      Call connector.get_person_communities(
        handle=person.platform_handles[platform]
      )
      Tag each result with the person's name.
  Update person's last_checked_at.

STEP 4 — COMBINE AND DEDUPLICATE:
Merge results from keyword and people discovery.
If the same community was found by both methods 
set discovery_method to both and merge the 
keyword and people lists.
Remove any communities that already exist in 
monitored_communities (status already_monitoring).
Remove any communities that already exist in 
community_suggestions with status approved 
or rejected (already processed).
Communities in community_suggestions with status 
pending are kept — they will be updated if 
new discovery data adds to them.

STEP 5 — SCORE:
Call CommunityScorer.score_batch() on all 
new communities.
Filter out communities below 
MIN_COMMUNITY_RELEVANCE_SCORE.
Sort by relevance_score descending.
Keep only the top MAX_SUGGESTIONS_PER_RUN.

STEP 6 — SAVE SUGGESTIONS:
Upsert all scored communities into 
community_suggestions with status pending.
For communities already in the table with 
status pending update their scores and 
discovery data — do not create duplicates.
Update community_discovery_runs record 
with counts and status completed.

STEP 7 — NOTIFY:
Update the processing_logs table with a 
summary: how many new communities were found 
and are awaiting the author's review.

ERROR HANDLING AND RELIABILITY
═══════════════════════════════════════

Platform-level isolation:
If community search fails on one platform 
continue with the others. Log the failure 
to processing_logs. Mark that platform as 
partially completed in the run record.

Rate limit handling:
Community discovery is less time-sensitive 
than post discovery. If a rate limit is hit 
wait for the full retry-after period before 
continuing. Do not rush.

Empty results:
If a platform returns no results for any 
keyword that is normal and expected. 
Log it as a debug message not an error.

People without handles:
If a person has no handle for a given platform 
skip that platform silently for that person.

Duplicate prevention:
The unique constraint on (platform, community_id) 
in both monitored_communities and 
community_suggestions prevents duplicates at 
the database level. Handle constraint violations 
gracefully.

Score failures:
If scoring fails for a batch of communities 
assign them a score of 0.0 and include them 
in the suggestions with a note that scoring 
failed. The author can still manually approve 
them if they recognise the community.
